
## 2024-04-18 - Authentication Bypass due to OIDC Claim Defaulting
**Vulnerability:** In `pkg/server/auth.go`, the `email_verified` claim was defaulting to `true` when it was missing from the token. This created a high-severity authentication bypass vulnerability where a malicious or misconfigured OIDC identity provider omitting the claim would automatically be treated as verified.
**Learning:** Never default to `true` or a permissive state when handling authentication or authorization claims. Secure defaults (fail-closed) are crucial when interacting with external identity providers.
**Prevention:** Always assume claims are unverified (`verified := false`) unless explicitly present and valid in the token. Implement thorough unit tests that verify behavior when claims are missing entirely, not just when they are present and invalid.
## 2024-06-05 - Raw Error Leakage (CWE-209) in API Responses
**Vulnerability:** The Go backend was returning raw internal errors to clients in various API responses by using `writeJSONError(w, err.Error(), ...)` or `writeJSONError(w, fmt.Sprintf("...", err), ...)`, causing an information leakage vulnerability (CWE-209).
**Learning:** Returning `err.Error()` or formatting errors into string responses can expose sensitive implementation details, database schema information, or internal API structures to potential attackers. Only user input validation errors should be explicitly returned to the client; all internal/system errors should return generic, safe messages while the detailed original error is strictly kept in server-side logs.
**Prevention:** Avoid passing raw `error` variables directly to client HTTP response functions (like `writeJSONError`). Instead, log the detailed error server-side and respond with generic, client-friendly error messages like "internal server error". Tests must be updated if they assert on exact original error strings from the response body.
