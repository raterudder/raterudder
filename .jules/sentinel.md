
## 2024-04-18 - Authentication Bypass due to OIDC Claim Defaulting
**Vulnerability:** In `pkg/server/auth.go`, the `email_verified` claim was defaulting to `true` when it was missing from the token. This created a high-severity authentication bypass vulnerability where a malicious or misconfigured OIDC identity provider omitting the claim would automatically be treated as verified.
**Learning:** Never default to `true` or a permissive state when handling authentication or authorization claims. Secure defaults (fail-closed) are crucial when interacting with external identity providers.
**Prevention:** Always assume claims are unverified (`verified := false`) unless explicitly present and valid in the token. Implement thorough unit tests that verify behavior when claims are missing entirely, not just when they are present and invalid.
## 2024-05-01 - Information Leakage in API Error Responses (CWE-209)
**Vulnerability:** Several HTTP handlers in `pkg/server` (like `settings.go` and `tesla.go`) were using `writeJSONError(w, err.Error(), ...)` or `writeJSONError(w, fmt.Sprintf("...", err), ...)`. This exposed raw internal details (like network timeouts, database errors, or encryption failures) to clients, creating an information leakage vulnerability.
**Learning:** Returning dynamic, underlying errors directly to clients is a security theater failure. It exposes internal architecture and state without providing actionable value to the end user. However, user input validation errors are safe to return dynamically.
**Prevention:** Always use static, sanitized string messages in external-facing error responses (e.g., `writeJSONError(w, "failed to verify ess credentials", ...)`). Ensure the original underlying error is still explicitly logged on the server side (e.g., `log.Ctx(ctx).ErrorContext(ctx, "...", slog.Any("error", err))`) to prevent swallowing errors and losing debug observability.
