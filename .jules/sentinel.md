
## 2024-04-18 - Authentication Bypass due to OIDC Claim Defaulting
**Vulnerability:** In `pkg/server/auth.go`, the `email_verified` claim was defaulting to `true` when it was missing from the token. This created a high-severity authentication bypass vulnerability where a malicious or misconfigured OIDC identity provider omitting the claim would automatically be treated as verified.
**Learning:** Never default to `true` or a permissive state when handling authentication or authorization claims. Secure defaults (fail-closed) are crucial when interacting with external identity providers.
**Prevention:** Always assume claims are unverified (`verified := false`) unless explicitly present and valid in the token. Implement thorough unit tests that verify behavior when claims are missing entirely, not just when they are present and invalid.
## 2026-05-09 - IP Spoofing Rate Limit Bypass via CF-Connecting-IP
**Vulnerability:** The application's `getClientIP` function blindly trusted the `CF-Connecting-IP` header before falling back to parsing `X-Forwarded-For`. This allowed an attacker to trivially spoof their IP address by injecting a fake `CF-Connecting-IP` header (e.g., `CF-Connecting-IP: 1.1.1.1`), completely bypassing rate limits since each spoofed IP would get a new bucket.
**Learning:** Only trust proxy-provided IP headers if you explicitly verify the request came from that proxy (e.g., by checking Cloudflare IP ranges). Otherwise, rely on `X-Forwarded-For` with proper anti-spoofing logic (parsing right-to-left to find the first public IP appended by the trusted proxy infrastructure).
**Prevention:** Remove blind trust of `CF-Connecting-IP`. `X-Forwarded-For` parsing handles both standard proxies and Cloudflare correctly without opening up a trivial spoofing vector for environments not running behind Cloudflare.
