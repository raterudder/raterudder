
## 2024-04-18 - Authentication Bypass due to OIDC Claim Defaulting
**Vulnerability:** In `pkg/server/auth.go`, the `email_verified` claim was defaulting to `true` when it was missing from the token. This created a high-severity authentication bypass vulnerability where a malicious or misconfigured OIDC identity provider omitting the claim would automatically be treated as verified.
**Learning:** Never default to `true` or a permissive state when handling authentication or authorization claims. Secure defaults (fail-closed) are crucial when interacting with external identity providers.
**Prevention:** Always assume claims are unverified (`verified := false`) unless explicitly present and valid in the token. Implement thorough unit tests that verify behavior when claims are missing entirely, not just when they are present and invalid.
## 2026-05-06 - Information Leakage (CWE-209) in Error Responses
**Vulnerability:** In multiple endpoints (`pkg/server/settings.go`, `pkg/server/tesla.go`), raw backend errors from underlying libraries or systems were being sent to clients via `writeJSONError(w, err.Error(), ...)` or formatted strings like `writeJSONError(w, fmt.Sprintf("... %v", err), ...)`. This could expose internal service details, dependency names, or network structures, creating an information leakage vulnerability (CWE-209).
**Learning:** Always sanitize API error responses. Distinguish between safe-to-display validation errors (e.g., input parsing) and internal system errors (e.g., database, external APIs).
**Prevention:** For internal errors, log the detailed error server-side (`log.Ctx(ctx).ErrorContext(...)`) and return a generic, static error string to the client. Avoid blindly echoing `err.Error()` in HTTP responses. Ensure tests verify the sanitized error message.
